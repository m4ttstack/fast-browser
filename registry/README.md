# Fast Browser registry: deploy runbook

The registry is a small personal-cloud service (push/pull/search over
compiled flow artifacts) meant to run as its own Railway project, deployed
from this same repo. This document is the operator's runbook: environment
assumptions, keygen, deploy and rollback commands, and how to smoke-test a
live deployment. It intentionally names every environment variable the
service needs; it never names, prints, or otherwise carries a value for any
of them.

## Environment assumptions

- Railway CLI installed and authenticated (`railway whoami` succeeds). If it
  is not, run `railway login` first; nothing below works unauthenticated.
- Railway project name: `fast-browser-registry`, containing two services: a
  Postgres database (pgvector-capable, see below) and the app service
  deployed from this repo's root.
- Environment variables the app service needs, by name only:
  - `REGISTRY_TOKEN` -- the bearer token clients authenticate with. Generate
    a fresh random value (for example `openssl rand -hex 32`); never reuse a
    token from another environment.
  - `REGISTRY_SIGNING_KEY` -- an Ed25519 private key, PKCS8 PEM. Generated by
    `registry/scripts/keygen.mjs` (see Keygen below). Never committed,
    never logged.
  - `DATABASE_URL` -- wired as a Railway variable reference to the Postgres
    service's own connection string, not typed in by hand.
  - `VOYAGE_API_KEY` -- optional. When set, the service embeds pushed flows
    and turns semantic clustering and search on; when unset, the service
    runs correctly in keyless mode (lexical search only, no clustering).
  - `PORT` -- injected by Railway at deploy time; the app service never sets
    this itself.

None of the above values belong in this file, in a commit, in a deploy
command's shell history in a form that echoes them, or in any report an
agent writes about a deploy. Every command below that sets a real value
reads it from a local file or a generator, never from a literal typed into
the terminal in a way that gets recorded verbatim.

## Keygen

Run once, when standing up (or rotating) a deployment:

```
node registry/scripts/keygen.mjs
```

This prints a fresh Ed25519 keypair: a private key PEM and a public key PEM,
each clearly labeled. The private key PEM becomes the Railway
`REGISTRY_SIGNING_KEY` value; paste it directly into `railway variables set`
(or the Railway dashboard), never into a file that gets committed. The
public key is printed for reference only and does not need to be stored
anywhere separately: once the service boots with the private key, it
derives and serves the matching public key itself from `GET /health`.

### Rotating REGISTRY_SIGNING_KEY

The service signs only at ingest (`registry/lib/ingest.mjs`): every
canonical's `signature` was computed once, at push time, under whatever key
was live then. Rotating `REGISTRY_SIGNING_KEY` changes what key the service
signs NEW pushes with; it does nothing to signatures already stored from
before the rotation. A client's `registry init` pins the service's CURRENT
public key (TOFU) and verifies every later pull against that ONE pinned
key -- so after a rotation, a pre-rotation canonical's old signature no
longer verifies against the new pinned key. This is loud and safe (a
verification failure, never silently-wrong data) but it makes that
canonical unpullable until it is re-signed. Skipping the re-sign step below
leaves every pre-rotation canonical unpullable indefinitely -- safe to defer,
never safe to forget.

Rotation steps, in order:

1. `node registry/scripts/keygen.mjs` -- generate the new keypair (same as
   Keygen above).
2. Set the new private key PEM as `REGISTRY_SIGNING_KEY` (`railway variables
   set`, or the dashboard) and redeploy. From this point on, every NEW push
   signs under the new key; every canonical pushed before this point still
   carries a signature from the OLD key.
3. Re-sign every existing canonical under the new key:
   ```
   railway run node registry/scripts/maintain.mjs --re-sign
   ```
   (or, running against the service's Postgres from a machine with
   `DATABASE_URL` and `REGISTRY_SIGNING_KEY` set locally to the same values
   the deployed service has: `node registry/scripts/maintain.mjs --re-sign`).
   This iterates every canonical, recomputes its canonical bytes, and
   re-signs any whose stored signature does not already verify against the
   current key -- safe to interrupt and re-run (a second run against an
   already-re-signed registry reports 0 updated), and it deliberately does
   NOT bump any canonical's `updatedAt`, so a rotation never looks like a
   content change to `GET /v1/pull?since=`.

   Before signing anything, each canonical's bytes are re-hashed and
   checked against its own stored `contentHash` -- the same check ingest
   itself makes on every push. A record whose content and contentHash have
   drifted apart (a direct DB edit, a bug, tampering) is **refused, not
   signed**: it is counted separately (`mismatched`), named by id and name
   in a warning line, and left exactly as it was -- re-signing is the one
   moment the trust chain is re-minted, and it must never be the weak link
   that launders a tampered record under a fresh, validly-verifying
   signature. A record whose content simply fails to parse is handled the
   same way under a separate counter (`failed`): named in a warning, left
   untouched, and never allowed to stop the rest of the pass -- one bad
   record no longer aborts the whole run. Command output is a per-action
   summary line (`scanned`/`updated`/`mismatched`/`failed`/duration) plus
   one warning line per refused or failed record; it never prints a flow's
   content and never echoes key material. **The process exits non-zero
   whenever any record was mismatched or failed** -- treat that as "run
   again after investigating the named records," not as the rotation
   having silently failed; every OTHER record still got re-signed in the
   same run.
4. Every client re-runs `registry init` against the service. A "the
   service's key changed" warning and a new fingerprint at this point are
   EXPECTED and LEGITIMATE -- this is the one case where that warning means
   "you just rotated the key," not "something is wrong." Re-running `init`
   re-pins the client to the new key.
5. Pulls verify again, against the new key, for every canonical that step 3
   actually re-signed. A canonical step 3 reported as `mismatched` or
   `failed` is still on the OLD key and still unpullable until whatever is
   wrong with its stored content is fixed and `--re-sign` is run again.

`registry/scripts/maintain.mjs` requires `DATABASE_URL` unconditionally (it
refuses to run against the in-process memory store -- maintenance there
would be meaningless, since nothing else can ever see it) and requires
`REGISTRY_SIGNING_KEY` for `--re-sign` specifically, validated the same way
boot does (an Ed25519 PKCS8 PEM, rejected loudly and by name otherwise).
Neither variable, nor any other secret, is ever echoed in its output.

### Embedding backfill

The same script also backfills embeddings:

```
railway run node registry/scripts/maintain.mjs --backfill-embeddings
```

(requires `VOYAGE_API_KEY`, same as ingest). Use this when some canonicals
have a null embedding -- either pushed during a keyless era (no
`VOYAGE_API_KEY` set at the time) or pushed while Voyage was degraded for
that one push (registry/lib/embedder.mjs's per-call failure contract). A
null-embedding canonical is invisible to semantic search (it can still be
found lexically, and still pulls/verifies normally) and never participates
in cluster-merge dedup. This pass only ever touches null-embedding records
-- it never re-embeds one that already has a value -- so it is safe to run
repeatedly; a per-record Voyage failure is counted and skipped (retried on
the next run) rather than aborting the whole pass, and like `--re-sign`, it
never bumps `updatedAt`. A record whose content fails to parse is counted
as `failed`, named in a warning, and left alone -- same containment as
`--re-sign`, and the process exits non-zero when `failed > 0`. Both flags
can be passed in the same invocation to run both passes back to back.

## pgvector requirement

The service's own migration (`registry/migrations/001-init.sql`) runs
`CREATE EXTENSION IF NOT EXISTS vector` as the very first statement, applied
automatically at boot (`registry/server.mjs`'s `boot()` calls the store's
`init()` before the HTTP listener ever starts accepting requests). The
Postgres service backing this deployment must be a pgvector-capable image --
Railway's standard Postgres template does not ship the extension, so use
Railway's pgvector-specific Postgres template (or any Postgres image that
bundles pgvector) when provisioning the database service. If the extension
is unavailable, boot fails loudly with a message naming the failure (with
`DATABASE_URL` redacted out of it) and the process exits non-zero rather
than starting in a half-migrated state.

## Registry-deps build note

`registry/` is its own npm package (`registry/package.json`, dependency:
`pg`) with its own `node_modules`, separate from the plugin root's
(intentionally dependency-free) `node_modules`. A build that only installs
the repo root leaves `registry/node_modules` missing and the service crashes
at boot with `ERR_MODULE_NOT_FOUND` the moment it tries to `import 'pg'`.
The committed `railway.json` build command handles this:

```
npm ci --prefix registry
```

and the deploy start command runs the service directly from the repo root:

```
node registry/server.mjs
```

with `healthcheckPath` set to `/health` so Railway's own health check hits
the one route that needs no auth. Nothing about this build/deploy pair
should need to change by hand; if it does, edit `railway.json`, not a
Railway dashboard setting that this file would otherwise silently disagree
with.

## Deploy gotchas

- **`.railwayignore`.** Railway's upload step indexes the whole working
  tree before it ever reaches build or deploy, and that indexer does not
  tolerate a dangling symlink. `tests/fixtures/legacy-home/.claude/skills/*`
  contains symlinks that are INTENTIONALLY dangling (they point at a
  fixture-only home directory path that only exists inside a test's
  synthetic HOME, never on real disk), and the first real deploy of this
  service failed indexing on exactly that. The committed `.railwayignore` at the
  repo root excludes `tests/`, `.superpowers/`, `.github/`, `skills/`, and
  `docs/` from the upload, both to fix the dangling-symlink failure and as
  general upload hygiene (none of those directories carry runtime code).
  This is safe: the deployed service's own import graph lives entirely in
  `registry/` plus the one `lib/flows/*` leaf module it imports
  (`artifact.mjs`, which itself imports nothing else in the repo) --
  nothing under `tests/`, `.superpowers/`, `.github/`, `skills/`, or
  `docs/` is ever imported at runtime, so excluding all of them from the
  upload cannot break the build or the running service.
- If `railway up` ever fails again on an upload/indexing error (as
  distinct from a build or boot error, which show up differently in the
  CLI's own output), check `.railwayignore` first for a newly-added
  directory with the same dangling-symlink or non-runtime-bulk shape,
  before assuming a Railway-side outage.

Confirmed working (this deployment has gone live): project
`fast-browser-registry`, service `registry`, reachable at
`https://registry-production-bea1.up.railway.app` (an example domain
Railway assigned; a domain isn't required for the service to run, only for
external callers to reach it), Node 20.20.2 selected via `engines`, build
`npm ci --prefix registry` per `railway.json`. `registry/scripts/smoke.mjs`
passed twice against it: first push `created`, second `deduped`, mode
`semantic` (`VOYAGE_API_KEY` set, clustering on) -- the same acceptance
shape documented in Smoke usage below, now confirmed against a real
deployment rather than only a local boot.

## Deploy commands

These are described at the verb level, since exact Railway CLI flags can
shift between versions; run `railway --help` (or `railway <verb> --help`)
as the authority on the current syntax if a command below no longer
matches.

1. `railway whoami` -- confirm authentication before anything else. If this
   fails, stop and run `railway login`.
2. `railway init` -- create (or link to) the `fast-browser-registry`
   project, if it does not already exist.
3. Provision the Postgres service (pgvector-capable, see above) inside that
   project, and the app service pointed at this repo's root.
4. `railway variables --set` -- set `REGISTRY_TOKEN`, `REGISTRY_SIGNING_KEY`,
   `VOYAGE_API_KEY` (optional) on the app service, and wire `DATABASE_URL`
   as a reference to the Postgres service rather than a typed literal.
   `PORT` needs no manual setting; Railway injects it.
5. `railway up` (or the deploy verb your CLI version uses) -- deploy the app
   service. `railway.json` supplies the build and start commands
   automatically.
6. `railway domain` -- generate (or attach) a public domain for the app
   service, if the deployment needs to be reachable from outside Railway's
   internal network.
7. `railway logs` -- tail the app service's boot output. Watch for the line
   `fast-browser-registry listening on port <port>`: `boot()` only reaches
   that print after the store's migration step (including
   `CREATE EXTENSION IF NOT EXISTS vector`) has completed successfully, so
   its presence is the confirmation that migrations applied and the
   pgvector extension is available. A boot failure instead prints a single
   line prefixed `fast-browser-registry: ` naming what went wrong (a
   missing required env var, a bad signing key, or a Postgres
   init/migration failure with `DATABASE_URL` redacted out of the message)
   and the process exits non-zero -- there is nothing else to page through
   in the logs beyond that one line.

### Rollback

Roll back by redeploying a previous, known-good deployment rather than
reverting code and redeploying forward: `railway redeploy` (targeting an
earlier deployment id, e.g. from `railway logs` or the dashboard's
deployment history) is the generic verb for this. Again, treat
`railway --help` / `railway redeploy --help` as the authority on the exact
invocation for whatever CLI version is installed.

## Smoke usage

`registry/scripts/smoke.mjs` is a standalone diagnostic (no external
dependencies beyond node's own runtime) that exercises health, push, pull
plus signature verification, and search against any already-deployed
registry:

```
REGISTRY_URL="<url>" FAST_BROWSER_REGISTRY_TOKEN="<token>" node registry/scripts/smoke.mjs
```

It pushes a fixed, clearly-namespaced canary flow (`smoke-test-canary`,
origin `https://smoke-test.invalid`) and never deletes it -- the registry
has no delete API, so the canary is expected to remain in the registry
permanently. Run it twice in a row after a fresh deploy: the first push
should report outcome `created`, and the second (byte-identical) push
should report `deduped` -- both are treated as passing outcomes, and seeing
that transition is the concrete proof that push idempotency works against
this deployment. The script prints a compact PASS/FAIL/SKIP line per step
and exits 0 only if every step passed; it never prints the token, and never
prints request headers unredacted.

## Client-side wiring

Once the service is deployed and smoke-tested, point the CLI at it:

```
fast-browser registry init <url>
```

and set the bearer token for every later `registry push` / `registry pull` /
`registry search` invocation via the `FAST_BROWSER_REGISTRY_TOKEN`
environment variable (never via a config file, and never the same token as
the one only the operator holds for admin-style diagnostics like the smoke
script, unless the two are deliberately meant to be the same value).
